Methods and curation pipeline

How the Ligandalyzer is built

E3 Ligase Ligandalyzer is a structure-first curated database resource. The public web application sits on top of a multi-step structural and cheminformatics workflow that retrieves recruiter-bound E3 ligase structures, standardizes recruiter identities, computes ligand descriptors and SASA features, assigns scaffolds, and packages release-aware tables for downstream database and download use.

Overview of the curation workflow

The current build logic is documented in the numbered workflow scripts from the public E3-Ligandalyzer-Scripts repository and the update-oriented utilities in E3_UPDATE_TOOL. The pipeline is intentionally staged: structure acquisition and cleanup happen before ligand metadata, SASA, scaffolding, database assembly, and dataset summary generation.

1

Acquire and prepare structures

0_LigaseCreator.py and 1_E3_Ligase_Preparer.py support future updates by creating ligase folders, downloading mmCIF structures, selecting ligands and protein chains, and exporting curated PDB assets with manifest and audit records.

2

Clean structural inputs

The historical build scripts fetch candidate structures, clean PDBs, split ligand-containing entries, and standardize chain naming before downstream analysis.

3

Annotate recruiter chemistry

Ligand metadata, SMILES mappings, duplicate-code handling, and descriptor calculation are generated before recruiter instances are packaged into crosswalk tables and the final SQLite database.

4

Compute SASA and scaffold context

SASA summary and atom-level tables are generated alongside recruiter scaffold mappings, scaffold-level summaries, and scaffold supercluster tables.

5

Build database and release summaries

17__BUILDdb.py assembles SQLite tables, and 18_Data_Summary.py regenerates manuscript-facing dataset summaries when upstream curation changes.

PDB and structure selection strategy

The structural workflow is explicitly recruiter-bound and structure-linked. Repository documentation describes a curated, literature-guided approach paired with PDB searches and validation rather than automated bulk harvesting alone. Audit notes in the local codebase emphasize a PDB → protein → E3 validation strategy rather than assuming that a ligase name is sufficient to validate a structure.

Curated entry discovery

Candidate structures are collected from curated E3 ligase lists, literature-guided searches, and expert PDB review. The update tool is designed to help append new ligase folders and new structure files in a controlled, reproducible way.

Ligand-containing complex preference

Pipeline and update-tool notes both prioritize ligand-containing entries over apo structures or artifact-only entries, because the downstream database is designed around recruiter-centric structural interpretation.

E3 ligase definition and normalization

Ligase identity is normalized as a first-class field across the database. Local audit notes describe validation steps that include organism filtering, protein identity confirmation, and novelty checking against the existing ligase inventory before newly curated entries are accepted into an update workflow.

The public methods page does not assign undocumented thresholds for organism, confidence, or entry inclusion. Where exact cutoffs are not exposed by the current codebase, they should be treated as configured in the curation pipeline and reported formally in future release manifests.

Recruiter ligand extraction

Recruiter extraction is handled through a sequence of structure cleanup, single-ligand isolation, and metadata reconciliation steps. The numbered scripts show that ligand-containing HETATM entries are separated, standardized, and later paired with SDF- and SMILES-derived metadata tables. The update tool mirrors the same philosophy interactively by asking the curator to retain the relevant ligand residue and protein chain before exporting curated PDB files.

LR code assignment

The database distinguishes between an underlying ligand identity and a curated structural recruiter instance. Public pipeline documentation defines the LR code as a curated recruiter/conformation/instance identifier, and the local database preserves that mapping through tables such as Recruiter_Master_Map, Recruiter_Code_Crosswalk, and Ligand_Instance_Recruiter_Codes.

Why LR codes exist

A single ligand can recur across multiple PDB entries, poses, ligases, or variants. LR coding keeps those structural contexts visible instead of collapsing everything into one chemical-only record.

Where code assignment is handled

Duplicate-code handling and synchronized LR-table cleanup are exposed in scripts such as 7B_RenameDuplicateLigandCodes.py, 10C_CLean.py, and 16_TBLCreation.py.

Handling duplicate ligands, conformations, variants, and alternate structures

Duplicate ligands are not treated as simple errors by default. The current resource preserves repeated structural instances when they reflect real differences in PDB context, ligand pose, or curated variant state. The local database uses fields such as Variant, pdb_id, PDB_File, and Instance_Key to keep those distinctions explicit.

Manual cleanup scripts are also present for exclusions and table harmonization. This means the workflow is semi-manual by design: duplicates can be retained, renamed, merged, or excluded depending on whether they represent meaningful structural context or problematic redundancy.

Scaffold generation and scaffold clustering

Scaffold generation is built into the current pipeline through Bemis–Murcko-style framework decomposition and later unification steps. Public script names and local tables indicate a staged process: recruiter-to-scaffold mapping, scaffold-level summary generation, advanced scaffold data assembly, supercluster assignment, and scaffold unification before final database packaging.

Scaffold generation

14_ligasescaffolds.py and related scaffold-data scripts populate recruiter-to-scaffold mappings and scaffold summaries used by the scaffold dashboards.

Clusters and superclusters

15B_ADV_ScafCluster.py and 15C_ScaffoldUnifier.py document the advanced clustering and unification stage. The live app exposes scaffold supercluster tables where available.

SASA calculation workflow and exposure definitions

SASA is a core resource feature rather than an afterthought. The current pipeline includes audited SASA calculation, SASA cleanup, ligand-level SASA summary tables, and atom-level SASA tables. In the public SQLite snapshot, each recruiter record can carry both aggregate exposure metrics and per-atom solvent exposure values.

Ligand-level SASA summary

The summary table reports total atoms, exposed atoms, total SASA in complex, and aggregate %Exposed and %Buried values for each curated recruiter instance.

Atom-level SASA

The atom table stores continuous Exposure_A2 values for each mapped atom. This supports 2D and 3D exposure visualization, attachment-vector inspection, and downstream filtering.

The current public tables explicitly define exposed atoms as atoms with measurable solvent exposure and keep exposure as a continuous SASA quantity. The site therefore supports a practical distinction between buried atoms, intermediate or partially exposed atoms, and strongly exposed atoms without claiming unpublished categorical thresholds.

Data quality checks, filters, and missing-data policy

The repository includes explicit audit and cleanup layers. Local audit documents describe true-ligase validation, artifact rejection, HETATM confirmation, novelty checking, and manual exclusion when structures or annotations do not meet curation expectations. Additional cleanup scripts remove or harmonize entries when table-level inconsistencies are discovered.

  • Artifact-like small molecules can be filtered before recruiter acceptance.
  • Manual exclusion and table clean-up steps are present in the pipeline.
  • Missing or incomplete public records are surfaced through the site’s missing-data and missing-recruiter pages rather than silently hidden.
  • Future update submissions should preserve manifest, audit, and provenance information whenever possible.

Reproducibility notes

Reproducibility depends on both the public web database and the companion curation repositories. The E3-Ligandalyzer-Scripts repository preserves the historical numbered build order, and the E3_UPDATE_TOOL repository explains how future updates can be appended in a more maintainable structural-ingestion workflow.

The current site is therefore best interpreted as a release-aware curated resource backed by an explicit script trail, not as a black-box database. The Version 1 release page and the human-readable download manifest should be treated as the public record of the current dataset state, while the raw JSON manifest remains available for machine-readable workflows.
